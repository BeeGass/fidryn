    A law module is a file of edition 2. It holds provisions of law as data, with their notes and what the source says of them, each named by an address and covered by hashes; or, written by hand, it gives names to provisions and binds names to them. Nothing in a law module is evaluated. Law modules stand in workspaces: a generated workspace holds what an importer writes from the archives of one release, and a curated workspace holds modules written by hand, which may depend on generated workspaces. fidryn check checks one module or a whole workspace, and fidryn changes says what changed between two releases.

    This reference gives, in this order: the two editions; the addresses of modules, provisions and notes, and the file path of a module; the normalization of text; the model of provisions, notes and layers; their hashes; the syntax of edition 2, with three modules written in it; what the checker verifies in one module; workspaces, their manifest and their lock, and what the checker verifies in one; how a workspace is checked, and the outcome of each reference; the cache of the check; the definitions that the ingester extracts and the patterns it reads them by; curated modules, their names, the dependencies of a curated workspace and its bindings; change sets; the ingester for the United States Code, what it reads and what it does not import; what is counted, in the coverage ledger and in the sample of the Code that the repository holds; and the limits of all of these.

    The crate fidryn-provision implements the model and the rules over it, fidryn-syntax reads the text of a module, fidryn-check lowers it into the model and checks it, fidryn-driver checks a workspace, writes a generated one and compares two, and fidryn-ingest-uscode imports the Code. In the examples, /zz/demo is an invented corpus.

    4.1 Editions #

    A .fr file is of one of two editions. A file of the first edition is a program of the language that Language describes, and carries no marker. A file of edition 2 is a law module: its first two significant tokens are the word edition and the integer 2; white space, line ends and comments before them are skipped. A file whose first significant token is anything else is a file of the first edition. A file that begins with the word edition followed by anything other than 2 is refused with E100: "unknown edition 3; this toolchain reads edition 2 after the word edition, and files of the first edition carry no marker".

    fidryn_syntax::edition::edition_of tells the edition of a file, and each entry point asks it before it reads the file. The command line asks it of a regular file only: an input that is no regular file, such as a pipe or /dev/stdin, could not be read twice, and every command reads it as a file of the first edition.

    fidryn check DIRthe checks of the workspace in the directory, every module of it included, as under Workspaces
    fmt, inputs, run, explore, explain, verify, diff, render, review and fileexit 1 with E100: "an edition 2 module holds provisions and is not compiled for evaluation; fidryn check reads it"
    fidryn_cli::compile_source and compile_module, and so the source pasted into the mill of uithe same E100
    the documentation check, cargo xtask docsa fenced block, untagged or tagged fidryn, whose first line that is not blank is edition 2 is a complete module and gets the checks of one module

    4.2 Addresses #

    An address names a module, a provision or a note. It is / followed by one or more segments separated by /:

    • A segment is never empty, never . and never ...
    • Two addresses are equal when their texts are equal byte for byte: /us/usc/t1/s8/a and /us/usc/t1/s8/A are different addresses. Addresses are ordered by the bytes of their text.
    • The full stop and the en dash occur in the identifiers of the United States Code: s1395i–3, rule71.1, s44...46. No identifier of the Code holds ~. An ingester writes ~, and only an ingester, to mark what it added to an identifier, as in s1932~2.
    • The first segment names the authority that issues the names below it, the second the corpus. Nothing interprets either.
    • The parent of an address is the address without its last segment. An address of one segment has no parent.
    • An address is within another when it equals the other or lies below it at a segment boundary: /us/usc/t1/s8/a is within /us/usc/t1/s8, and /us/usc/t1/s80 is not.

    In JSON an address is a string that holds its text. A string that is no address is refused when it is read.

    Address::parse refuses a text that is no address and names the fault, with the segment it lies in, counted from 0:

    TextRefused because
    the empty textit is empty
    us/usc/t1it does not begin with /
    /us//t1segment 1 is empty
    /us/usc/segment 2 is empty
    /us/./t1, /us/../t1segment 1 is . or ..
    /us/usc/t1 s8, /us/usc/t1_s8, /us/usc/t1%20s8segment 2 holds a space, _ or %

    4.3 File paths #

    A module with address A is the file layout::module_path(A) under its workspace's root:

    1. Each segment of the address maps to one path segment, character by character:

      Character of the addressIn the path
      a lower-case ASCII letter, a digit or ~kept
      an upper-case ASCII letter_ followed by its lower-case form
      the en dash U+2013-
      the ASCII hyphen%2D
      a full stopkept, except as the first or the last character of a segment and before the letters fr that end a segment, where it is %2E

    2. If the mapped segment, or its part before its first full stop, compared without regard to case, is one of con, prn, aux, nul, com1 to com9 or lpt1 to lpt9, its first character is written as % followed by the two upper-case hexadecimal digits of its code.

    3. The path is the mapped segments joined by /, followed by .fr. The separator is / on every host.

    No path segment begins with a full stop, and none ends in a full stop or in .fr, so the file of one module never has the name of another module's directory: /zz/demo/a.fr/b is zz/demo/a%2Efr/b.fr, beside the file zz/demo/a.fr of the address /zz/demo/a.

    The mapping is one to one, so two addresses never share a path, also on a file system that ignores case: /zz/demo/ch6A is zz/demo/ch6_a.fr and /zz/demo/ch6a is zz/demo/ch6a.fr.

    layout::address_of_path reads a path back as its address. It refuses every path that the three rules do not write, such as zz/demo/CH1.fr, zz/demo/a_.fr, zz/demo/a%2d.fr, zz/demo/a%5F.fr, zz/demo/con.fr, zz/demo/.a.fr, zz/demo/a.fr/b.fr, zz/demo/a.txt and zz\demo\a.fr. The path zz/demo/a-b.fr is the address /zz/demo/a–b, with an en dash.

    4.4 Normalization #

    The text of a law module is normalized. normalize::normalize normalizes a text in four steps:

    1. Put the text into Unicode Normalization Form C.
    2. Replace each of the 25 characters with the Unicode property White_Space with U+0020: U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000.
    3. Replace each run of U+0020 with one.
    4. Remove U+0020 at the start and at the end.

    Nothing else changes: no case folding, and no change to quotation marks or dashes. U+200B (zero width space) and U+FEFF are not white space and are kept. normalize::is_normalized tells whether a text is normalized, that is, whether normalizing it leaves it unchanged.

    §, U+202F, 1§ 1
    Current, U+2000, throughCurrent through
    a, tab, b, line feed, c, carriage return, line feed, da b c d
    e, U+0301é (U+00E9)
    1, U+00A0, 0001 000
    U+3000, a, U+1680a

    U+FEFF, aunchanged

    The unit of normalization is the block: a paragraph, a heading, a number or a paragraph of a table cell. The text of a block is the words of its runs, concatenated, and that text is normalized: a run may begin or end with a space, a block may not.

    4.5 Provisions, notes and layers #

    A module of law has one of three shapes:

    • A unit holds one tree of provisions, whose top provision has the module's address. It also records the other addresses the source gives it (aliases), the container it stands in (within), the member of the source archive it was read from (source) and whether the source marks it as positive law (positive_law, which may be unknown), and it holds a source credit, notes, footnotes and definitions.
    • A container, such as a chapter, has a kind, a number, a heading and a status of its own and lists its members: the containers and units directly below it, in document order. It holds a source credit, notes and footnotes, and records aliases, within, source and positive_law as a unit does.
    • A curated module is written by hand. It imports modules, names addresses (citations) and binds names to provisions (bindings). A binding records the release it was made against and two hashes, one of the provision and one of the enacted notes of its unit, which tell when it is stale.

    The crate holds the model in its module model.

    4.5.1 Provisions #

    A provision has an address, a kind, a number, a heading and a status, each of the last three optional, and its items: text parts and child provisions, in document order. The address of a child lies below the address of its parent.

    • The kind and the status are identifiers, such as section and repealed. The model gives them no meaning and knows no list of them. A provision without a status is in force.
    • A number has a value, its machine form, and the text it is shown as, which may hold a footnote marker: the value 8 shown as § 8..
    • A text part has a role and at least one block:
    RoleThe part holds
    chapeauthe words that lead into the children
    contentthe text of the provision
    continuationwords that follow children
    provisoa proviso

    4.5.2 Texts and blocks #

    A text is a list of runs:

    RunHolds
    wordsplain words
    linkthe linked words, and the target as the source writes it
    superscriptsuperscript words
    subscriptsubscript words
    footnote markerthe marker as shown, and the number of the footnote it points at

    The plain text of a text is the words of its runs, footnote markers left out, concatenated; it is the text that is normalized. Text::from_runs merges adjacent runs of words into one and drops every run whose words are empty. A footnote marker has no words of its own and is kept.

    A block is a paragraph, a subheading, a table, quoted content or an image:

    • A table is a list of rows. A row belongs to the head, the body or the foot of its table and holds cells. A cell is a header cell or not, spans one or more columns and one or more rows, and holds blocks. An empty cell holds none.
    • Quoted content has the origin the source names for it, if any, and items: blocks, text parts and levels. A level, such as a quoted section, has a kind, an optional number, an optional heading and items of its own, and no address.
    • An image names the source of its picture. The picture is not part of the model.

    4.5.3 Notes, footnotes and definitions #

    A note has an address, a layer, the group word of the source (ungrouped when there is none), its topics, an optional heading and blocks. The layer of a note is enacted or editorial. A note belongs to the unit or the container it is anchored in.

    A footnote belongs to its module. The footnotes of a module are numbered from 1 in document order; each has the marker it shows and its blocks. A footnote marker names its footnote by that number.

    A definition records the provision that holds it (at), the terms it defines, its kind (means, includes, does_not_include or borrowed), the words that state its reach or none when the text states none, its condition when it has one (condition), the region the reach covers, its basis (enacted, restated or unresolved), what a borrowed definition takes its meaning from, either the target of a link (borrowed_from) or, when its source is not linked, the source words (borrowed_words), and a note to read with it (see_note). A definition of kind borrowed has exactly one of borrowed_from and borrowed_words, and a definition of any other kind has neither. The ingester for the Code extracts them by the rules of Definitions.

    enactedthe enacted notes
    editorialthe source credit, the editorial notes, the footnotes and the footnote markers

    4.6 Hashes #

    A hash is 32 bytes of BLAKE3, written as 64 lower-case hexadecimal digits. Hash32 reads only that form: a text of another length, or one with an upper-case or any other character, is refused and the fault is named.

    Every hash is BLAKE3 over a sequence of frames. A frame is one tag byte, the length of its value as eight bytes little-endian, and the value. The first frame of every hash has the tag 0x00 and holds a domain string. Below, ‖ is concatenation and F(t, v) the frame with tag t and value v:

    WhatFrames
    a text TF(0x10, UTF-8 of the plain text of T), then for each run that is not words, in order: a link F(0x11, start ‖ end ‖ UTF-8 of its target); a superscript F(0x12, start ‖ end); a subscript F(0x13, start ‖ end); a footnote marker nothing. start and end are byte offsets into the plain text, eight bytes little-endian each, end exclusive.
    an absent textF(0x1F, empty)
    a blocka paragraph F(0x20, text); a subheading F(0x21, text); a table F(0x22, table); quoted content F(0x23, quoted); an image F(0x24, UTF-8 of its source)
    a tablefor each row F(0x30 + group, cells), with the group 0 for the head, 1 for the body and 2 for the foot; a cell is F(0x34, colspan ‖ rowspan ‖ blocks), or F(0x35, ...) for a header cell, each span four bytes little-endian
    quoted contentF(0x40, UTF-8 of the origin, or empty), then each item: a block as above, a part as below, a level F(0x41, F(0x01, kind) ‖ number ‖ heading ‖ items)
    a numberF(0x02, UTF-8 of the value) ‖ F(0x03, the shown text as a text), or F(0x04, empty) when there is none
    a text partF(0x50 + role, blocks), with the role 0 for chapeau, 1 content, 2 continuation and 3 proviso
    a provision (its tree hash)BLAKE3 of F(0x00, "fidryn.provision/v1") ‖ F(0x01, kind) ‖ number ‖ heading ‖ F(0x05, status or empty) ‖ items, where a text part is as above and a child is F(0x60, its tree hash)
    a noteBLAKE3 of F(0x00, "fidryn.note/v1") ‖ F(0x70, group) ‖ F(0x71, topics joined by one space) ‖ heading ‖ blocks
    a containerBLAKE3 of F(0x00, "fidryn.container/v1") ‖ F(0x01, kind) ‖ number ‖ heading ‖ F(0x05, status or empty), then F(0x61, address) for each member in order
    the enacted layerBLAKE3 of F(0x00, "fidryn.layer.enacted/v1"), then for each enacted note in the byte order of its address F(0x72, address) ‖ F(0x73, note hash)
    the editorial layerBLAKE3 of F(0x00, "fidryn.layer.editorial/v1") ‖ the credit as a text, or an absent text, then the editorial notes as in the enacted layer, then for each footnote in ordinal order F(0x74, UTF-8 of its marker) ‖ blocks, then for each footnote marker of the module in document order F(0x75, UTF-8 of the address it is recorded with) ‖ F(0x76, UTF-8 of the marker as shown) ‖ F(0x77, its footnote number as four bytes little-endian)
    the operative layerof a unit, the tree hash of its top provision; of a container, its container hash

    The address of a provision is not in its tree hash, and the address and the layer of a note are not in its hash. Definitions are in no hash. A container's credit is in its editorial layer and not in its container hash.

    The document order of the footnote markers of a unit is: the tree of provisions depth first, taking for each provision its number, its heading and then its items in order; then the credit; then the notes in the byte order of their addresses, as the layers take them, the heading of each before its blocks; then each footnote in ordinal order. For a container it is its number, its heading, its credit, its notes in the same order, and its footnotes. A marker in a provision is recorded with that provision's address, and a marker in a note, its quoted content included, with the note's address. A marker in a credit, in a footnote, or in a container's own number or heading is recorded with the module's address.

    What follows from these rules:

    • A change to any word, number, heading, status, link target or link extent, superscript, subscript, table cell or span of a provision changes its tree hash and the tree hash of every provision above it, and of no other provision.
    • A footnote, a footnote marker, and the provision a marker stands in change the editorial layer and nothing else. Where in its provision a marker stands is in no hash.
    • The notes and their footnote markers are taken in the byte order of the notes' addresses, so the order in which a module lists its notes changes no layer hash. Moving a note to a new address changes the hash of its layer and not the note's own hash.

    hash::hash_provision, hash::hash_note, hash::hash_container, hash::layer_hashes_of_unit and hash::layer_hashes_of_container compute them. hash::tree_hashes gives the tree hash of every provision of a tree in document order, hashing each provision once. A second implementation in Python, conformance/hash_vectors.py, computes the same hashes of the invented models in conformance/fixtures/hash/vectors.json, and the tests of both hold their values to the digests recorded there.

    4.7 Syntax #

    The tokens are those of the lexer of the first edition. Words such as module and content are identifiers that the parser compares by their text. A string is a JSON string literal. Line ends are not significant, and // begins a comment that runs to the end of its line.

    A link [words -> target] holds the linked words and the target as the source writes it; sup and sub hold superscript and subscript words; mark "1" 2 is a footnote marker shown as 1 that names footnote 2. A num holds the value of a number and the text it is shown as.

    The parser, fidryn_syntax::e2::parse, enforces the grammar and stops at its first error, an E100 at the token it is about:

    • Every block has the fields shown, in the order shown. A word that is no field of its block is "unknown field <word> in <block>"; a field that stands out of its order, twice, or not at all is named as such, and so is a field given with another that takes the same place (borrowed_from and borrowed_words).
    • A word that begins no declaration is "unknown declaration <word>".
    • Text after the closing brace of the module is an error.
    • A source holds at most 64 MiB and 16,777,216 tokens, and its blocks nest at most 64 deep: "module exceeds resource limits".

    A module has one of three shapes. A unit has exactly one provision at the top, a container module exactly one container, and a curated module neither. alias, within, source, positive_law, credit, note, footnote, definition and layers belong to units and containers; import, citation and binding belong to curated modules. within, source, positive_law, credit and layers stand at most once, and a unit or a container has a source and layers. A container holds no provision, so a definition in a container module names no provision of its module. The declarations may stand in any order.

    The canonical form is what fidryn_provision::render::render writes, and generated modules are always in it:

    • UTF-8, \n line ends, a final line end, two spaces of indentation for each open brace, no blank line, no trailing space.
    • Line 1 is edition 2, line 2 is module "<address>" {.
    • The declarations in this order: each alias, within, source, positive_law, the provision or the container, credit, the notes in document order, the footnotes by ordinal, the definitions in the document order of the provisions they name and then by their first term, and layers. A curated module has its imports, then its citations, then its bindings, each in the order of its list.
    • One field to a line. A text is written on one line, its runs separated by one space.
    • A string is written with \\ for a backslash, \" for a quotation mark, \u00XX with lower-case hexadecimal digits for a character below U+0020 or U+007F, and every other character as itself.
    • A part or a cell whose content is exactly one paragraph is written in the short form (content "..."), otherwise in the brace form with one block to a line. A cell with no block is written td "", and that spelling is read back as a cell with no block. The shown form of a number that has none is written "" and read back as the empty text. Besides these two, an empty string stands only where the source itself may give an empty value: the value of a number, the shown form of a footnote and of a marker, the source of an image, and the target of a link. Anywhere else an empty string is refused: as the words of a run, as a term, as stated reach words, as a condition, as borrowed_from, as borrowed_words, as source, as the release of a binding, as a topic, and as the origin of quoted content.
    • span <colspan> <rowspan> is written only when one of the two is not 1.
    • Every hash and the three values of layers are computed by the rules of Hashes from what is written above them.

    fidryn_check::e2::lower reads a parsed module back into the model: lowering the parse of what render writes gives the model back. A unit, with invented text, in the canonical form:

    This module is unit.fr. Beside it, container.fr is a container module and curated.fr a curated module that binds two provisions of the unit. The tests of fidryn-check hold the three files to what render writes, and the documentation check checks the module above.

    4.8 What the checker verifies in one module #

    fidryn check FILE and the documentation check run fidryn_check::e2::check_source on a module of edition 2: the marker, the grammar, lowering into the model (lower), and the checks over the model (check_module). Every diagnostic carries the span of the text it is about. fidryn check prints each as FILE: CODE Title: message and exits 1, or prints ok.

    A definition names a provision of the unit; each term stands in that provision's text; the reach words, when stated, stand in its text or in the chapeau of one of its ancestors; the condition, when there is one, stands in its text or in the chapeau of one of its ancestors; the kind is means, includes, does_not_include or borrowed and the basis enacted, restated or unresolved; a borrowed definition has exactly one of borrowed_from and borrowed_words, and a definition of another kind has neither; borrowed_words, when present, stand in the provision's textE710
    In a curated module, no name is declared twice, its citations and its bindings sharing one set of namesE200

    An address is below another when it lies within it and is not the same address. The text of a provision is the text of each paragraph and subheading of its text parts, those in its tables and its quoted content included, and none of its children's; a term stands in it when one of those texts holds the term. Each of those texts is made of its runs in order without its footnote markers, which have no words, and without its superscript runs made only of the digits 0 to 9, which are footnote numbers marked as superscripts. With each such run one space goes too: the space just before it, when just after it there is a space or the end of the text; or, when it begins the text, the space just after it. A superscript run that holds anything else, and a digit written in any other run, is text. So section 5 of the Gadget Act stands in a paragraph written "... section 5 " sup "1" " of the Gadget Act.". The terms, the reach words, the condition and borrowed_words are all looked for in this text, and the chapeaus of the ancestors are read the same way. Every text holds the empty string, so an empty term, empty reach words, an empty condition or empty borrowed_words would pass the checks of a definition without checking anything. The topics of a note and the origin of quoted content have rules of their own because the hash of a note joins its topics with one space and the hash of quoted content takes an absent origin as an empty one: without them, two different modules could have one hash.

    An address or a name declared twice is reported at its later declaration, with the earlier one as a related span. A footnote is reported at its number when the number is not one more than that of the footnote written before it, the first being 1.

    A text that is not normalized is reported at the run where it first differs from its normalized form. A hash that does not match is reported at the hash, with the hash computed from the module. A change to one word of a provision is therefore reported at the hash of that provision, at the hash of every provision above it, and at the operative value of layers, since each of them covers the word. When lowering finds an error, the module is not lowered and the checks over the model do not run: a module whose text is not normalized is not also checked for its hashes.

    4.9 Workspaces #

    A workspace is a directory with a manifest, workspace.json, at its top. Every .fr file in it is a module of edition 2 whose address is below the manifest's prefix and which stands at the file path of its address. An entry whose name begins with a dot, whether a file, a directory or a symbolic link, is not the workspace's: the check does not read it, nor anything in it, unless it is told to keep its cache there, and the writer leaves it alone, so a repository's .git, a .gitignore or an editor's lock link may stand in a workspace. No symbolic link is followed, and one whose name does not begin with a dot is an error.

    • kind is generated or curated. A generated workspace is written by an importer from the archives of one release: its manifest has that release, and it has no dependencies. A curated workspace is written by hand: its manifest has no release key.
    • Each dependency of a curated workspace names a generated workspace with its name, its directory path, relative to the manifest's directory with / between its segments, its release, and lock_digest, the BLAKE3 of the bytes of its lock (Depending on another workspace).
    • toolchain is the version of the toolchain that whoever wrote the manifest recorded; the importer records its own. No check writes it: a check compares it with its own version and reports a difference as W760, a warning.

    A generated workspace has a lock, law.lock.json, beside its manifest; a curated workspace has none. The lock records the archives the workspace was made from, what the importer counted, and the BLAKE3 of the bytes of every module file by its path:

    url, retrieved_at, bytes, blake3 and sha256 of an artifact are those of the archive in the retrieval record, retrieval.json, which stands beside the archives of one release and is written when they are downloaded:

    4.9.1 Writing a generated workspace #

    An importer writes a generated workspace with fidryn_driver::workspace::GeneratedWriter:

    • create(out, manifest) takes the manifest of a generated workspace with a release and no dependencies, and a directory out that does not exist, holds nothing but entries whose name begins with a dot (the working directory of a new repository, with its .git, is such a one), or holds a generated workspace of the same prefix. Such a directory may also hold its coverage ledger, coverage.json, at its top, which the run writes again, and anywhere any entry whose name begins with a dot, which the run leaves as they are. Each of its .fr files must be the output of an earlier run: a module of edition 2 whose address lies below the prefix and which stands at the path of its address. create reads the head of each, the first significant tokens up to the brace after the module's address, which must lie in its first 64 KiB, before it writes anything. Any other directory, a curated workspace, a generated workspace of another prefix, one that holds a symbolic link of another name, and one that holds a .fr file of the first edition, a module of another prefix or a module at another path among them, is refused, with every such .fr file named, and nothing in it is changed. create writes workspace.json at once, through a temporary file like every file of the run, and clears the temporary files that an earlier run which was stopped left behind. One entry whose name begins with a dot is the writer's own and is not left alone: .fidryn-write at the top of the workspace, the directory of the temporary files of a run, which create clears and finish removes.
    • write(module) writes a unit or a container whose address is below the prefix, in the canonical form, to its path, through a temporary file that is renamed, and keeps the module's interface, built from the module as it was given. It may be called from several threads at once, and it fails when the run has already written a module to that path, so that no module replaces another.
    • finish(generator, artifacts, addresses, not_imported) removes every module of an earlier run, found by create, that the run did not write, and each directory that leaves empty, then writes law.lock.json, then, last, coverage.json, the coverage ledger counted from the interfaces of the modules it wrote, the manifest and the lock, and returns the lock. Nothing is read again to count the ledger: neither the text of the modules nor what the importer read.
    • compare(out, manifest) makes a writer that writes nothing. It compares the manifest with workspace.json at once, write compares each module with the file at its path, and finish compares the lock with law.lock.json and the ledger with coverage.json. finish counts as extra every .fr file of out that the run did not write and every entry that create refuses: a file other than a module, the manifest, the lock and the ledger at the top, and a symbolic link or any other entry that is neither a file nor a directory. A .fr file that create refuses for its head is extra where the run writes nothing, and different where it writes a module. The two follow one rule, so they cannot disagree. Only the entries whose name begins with a dot are not looked at. finish returns the lock when nothing differs, and then create accepts the directory and a run of the same modules changes none of its bytes; otherwise it returns WriteError::Differs, which lists every path that is missing, extra or different, in the byte order of the paths. A directory that does not exist lacks every file and is not made.

    What a run writes depends only on its modules, its manifest and what finish is given: neither the order of the calls nor the number of threads changes a byte. A run that is stopped before finish, by an error or because it was killed, leaves a generated workspace of the same prefix whose lock is missing or is that of the run before it. fidryn check reports it with E730, and the next run accepts the directory and, when it finishes, puts it right. A run stopped after the lock and before the ledger leaves a workspace that checks clean, since no check reads the ledger, and whose ledger is missing or is that of the run before it; compare reports it as missing coverage.json or different coverage.json, and the next run puts it right.

    4.10 How a workspace is checked #

    The check of a workspace runs in two phases.

    1. Phase one, for each module file by itself, of the workspace and of each of its dependencies that passes the checks of its entry, its manifest and its lock: the BLAKE3 of its bytes, its edition, the grammar, lowering, the checks of one module, and the module's interface. What it gives of a file depends on the file's bytes alone, so it is kept in the cache, and a file whose bytes were checked before is not checked again.
    2. Phase two, with the result of every module in memory: the BLAKE3 of each file against the lock of a generated workspace, and where each module stands, below the prefix and at the path of its address; and the check of each dependency by itself. Then, from the manifest and the interfaces alone, the manifest's toolchain, the within of every unit and container and the members of every container, the imports and the names of every curated module, the staleness of every binding, the addresses that two modules declare, and the outcome of every reference and of every citation. Phase two reads no module again. fidryn_driver::workspace::check_interfaces is that last part as a function of the interfaces of the workspace, what is known of each of its dependencies (the name, the release, the prefix and the interfaces of one that passed its checks, the prefix, when it is known, of one that failed), the manifest and the toolchain's version.

    Phase one runs on --jobs worker threads, by default as many as the system reports as available, each module file being read and checked on one of them; the module files of each dependency are read on the same workers, one dependency after another. Of phase two, the outcomes of the references and the citations are found on as many threads, the modules shared out among them; the rest of it, the comparison with the lock, where each module stands, the checks of each dependency, the manifest, within and members, imports and names, the staleness of the bindings, and the index of addresses the outcomes are looked up in, runs on one thread. The diagnostics, the summary line, the check report and the unresolved list are the same, byte for byte, for every number of workers: each module's result is collected by itself, and the results are sorted by the path of their file and then by position before anything is printed or written.

    4.12 The cache #

    What phase one gives of a module file depends on the file's bytes alone, so it does not change while the file does not. The check keeps it in a cache on disk, and a check that finds there the entry of a file's bytes takes phase one's result from it, instead of lowering and checking the module again. Phase two runs in full every time. A check of a workspace in which nothing changed reads the bytes of each module file, to find its entry, and the entry, and does none of the rest of phase one.

    An entry holds the result of phase one of one file: the BLAKE3 of its bytes, which phase two compares with the lock; its diagnostics, with their spans, none of which names the file; and the module's interface, or none when the module does not lower. Nothing that depends on the path of the file, on the lock, on the manifest or on another module is in it, so two files with the same bytes, in one workspace or in two, share one entry.

    The key of an entry is the BLAKE3 of four frames, built as the hashes are:

    The toolchain's version is the one fidryn --version prints. The identity of the executable is the BLAKE3 of the file of the running fidryn, as 64 hexadecimal digits: two builds of one version can differ in what phase one does, and an entry that another build wrote is never read. When that identity cannot be read, the check keeps no cache, and fidryn check says so once on stderr. A file larger than the largest source of edition 2 is not kept; the check refuses it in any case.

    The entry of a key is the file v1/<the first two digits of the key>/<key>.json in the cache's directory. That directory is the one --cache-dir names; else the one the environment variable FIDRYN_CACHE_DIR names, when it is set and not empty; else fidryn in the cache directory of the user, outside every workspace: on Windows the directory LOCALAPPDATA names, and on other systems the one XDG_CACHE_HOME names, else .cache in HOME, each taken only when it is an absolute path. That directory is not used when it is the directory of the workspace under check or lies inside it, as it does when one of these variables names a directory inside the workspace; the two are compared with every link and every .. resolved, as far as each exists. When none of them names a directory, or the one they name lies inside the workspace, the check keeps no cache, as with --no-cache, and fidryn check says so once on stderr, with the reason. --no-cache keeps no cache: the check then reads and checks every module file and writes no entry. Unless the cache is named inside it, the check writes nothing into the workspace, and it reads nothing there but the workspace's own files: a .fidryn-cache or any other entry whose name begins with a dot is not read, and a symbolic link of any name is not followed.

    One cache serves every workspace of a user. An entry is the result of the bytes of one file, whatever workspace holds the file, so the workspaces that hold a file of the same bytes share its entry, and the first check of a workspace may read some of its modules from the cache. The module files of the dependencies of a curated workspace are read through the same cache, and the check keeps no cache when the cache's directory and the directory of a dependency overlap, as Depending on another workspace describes.

    A check trusts its cache. An entry that is what the writer writes is taken as the result of the bytes it names, and its key is no secret: each of its frames can be known, and the identity of an executable that is published can be computed by anyone. Whoever can write in the cache's directory can therefore make a check pass a module whose hashes do not match its text, leave a module out without a diagnostic, or hide a stale binding. A cache belongs where only people one trusts can write, which is why the default is a directory of the user. A cache named inside the workspace it serves, with --cache-dir or FIDRYN_CACHE_DIR, is the user's choice and is used. Its entries then go with the workspace when it is copied or committed, and a check of a copy that came from someone else, with that cache named, takes as results whatever they put there. Its entries are also files of the workspace, and unless its name begins with a dot, the writer of a generated workspace refuses the directory for them.

    An entry is one line of compact JSON with these keys, in this order: schema, which is fidryn.cache/v1; key; digest, the BLAKE3 of the file's bytes; diagnostics, each as fidryn_core::Diagnostic writes it, with code, message, primary_span, related_spans and suggestion; and interface, the object that the JSON of an interface holds under interface, or null.

    Each worker of phase one looks up the entry of the file it reads by the entry's path; the cache's directory is never listed. An entry is read back only when it is what the writer writes: its JSON value is the value that what is read from it writes back, its key is that of its name, its digest is that of the file's bytes, and its interface names only what it holds, as Interface::from_json requires. Any other entry, one cut short, one that is not JSON or is JSON of another shape, or one copied from another key, is ignored: the module is checked again and its entry written again. An entry that cannot be read is missing in the same way.

    No read of a check sees an entry that the same check wrote: the entries of the files whose entries were missing are written once every file has been read, one for each key. So two module files of the same bytes in one workspace are both checked when the cache holds neither, and the count from cache is the same for any number of workers. An entry is written to a temporary name in its directory and then renamed, so that a reader never sees half of one, and two checks at once, of one workspace or of two, which may write the same entry, leave a valid cache; a check may read an entry that another check wrote while it ran. A failure to write the cache, such as a full disk or a directory that cannot be made, does not fail the check: no further entry is written, and fidryn check says once on stderr that the cache could not be written, naming the cache's directory and the error, and goes on.

    4.13 Definitions #

    The ingester for the United States Code extracts definitions from the provisions of every unit it imports, once the unit's provisions and notes are read, and writes each in the unit's module as a definition block (Syntax): the provision that holds it, its terms, its kind, the words that state its reach, its condition when it has one, the region the reach covers, its basis, and, where the rules give them, what a borrowed meaning is taken from, the target of a link or the source words, and a note to read with it.     4.13.17 What the values mean #

    • unstated: neither the paragraph, nor the reach line its part begins with, nor a chapeau above it states a reach in the forms these rules read. A reach stated somewhere else, for example in another subsection of the same section, is not read, so a definition whose words are unstated may still have a reach that the text states elsewhere.
    • condition: the words that say in what case the definition holds, as the text writes them: before the terms, at the end of the reach's Object, in a chapeau above, in the aside after the terms, or after the verb form. The rules record the words and do not read them; the region does not depend on them.
    • unresolved: the rules found no region. That includes reach words that name a part of the Code in a form the rules do not resolve, such as "this chapter and chapter 5", "subparagraph (A) of this paragraph" or, of a court rule, "this Rule 3021", a reach that names a law outside the Code, such as "this Act" or a link to a public law, and a reach whose kind word names neither the provision that states the reach nor any provision or container above it, whatever its words link to. Reach words of the first two kinds that are the words of one link to an address below the prefix are resolved: the region is the link's target, so "this Act" written as a link to a section of the Code has that section as its region. For an inherited reach, the provision that states it is the provision of the chapeau.
    • restated: the file does not declare its title positive law (its flag is no, or it has none), so the words of the provision are those of the editors of the Code, and the reach the law enacted may differ from the one they state: a "this chapter" of the Code may stand for "this Act" or "this title" of the law the editors classified there. see_note, when a definition has one, is the address of the first editorial note headed "References in Text" one of whose own paragraphs holds, in any case, the words that name the region followed by , referred to in. Such a note often says what the enacted words were; the rules do not check that it does.
    • borrowed_words: the words that name the source of a borrowed meaning when no link after the verb form names it, or when the meaning is made by regulations, rules or an order under the linked provision, as the text writes them. No section number in them is resolved to an address: they name the source and do not point at it.

A reference or a citation whose target is an address that lies where nothing is known is left out of the counts of the check report and of the unresolved list, an import of a module there is not reported, and a binding of an address there is not judged, since the one diagnostic of the dependency is the report; a target that is no address is malformed all the same. The check exits 1.

    But for one layout that Limits names, the check writes nothing inside the directory of a dependency, with any cache or with none: the entries of the module files of a dependency go into the cache of the check of the workspace, under the keys of their bytes as every entry is, so that the next check reads them from there. When the cache's directory and the directory of a dependency that the manifest names, whatever the checks of the entry find, are the same, or one lies inside the other, the check keeps no cache at all. The cache's directory lies inside the dependency's when it is named inside it, such as a .fidryn-cache of the dependency, or inside a workspace that stands in a directory of its dependency; the dependency's lies inside the cache's when it stands where the cache writes its entries, at v1 in the cache's directory, or anywhere else below it. The check then reads and writes no entry, says so once on stderr, as the cache could not be used, and the check went on without it: DIR: ... with the cache's directory, the dependency and which holds which, and goes on. Its diagnostics, its report and its exit status are then those of a check with --no-cache. The paths are compared with every link and every .. resolved, and of a directory that does not exist yet, the part that exists is resolved and the rest taken as written; a cache's directory that does not exist yet lies inside a dependency when the part of it that exists does. Only the two directories themselves are compared: a symbolic link below the cache's directory that leads into a dependency is followed when an entry is written through it.

    The summary line and the check report are about the workspace that is checked. modules and from cache count its own module files, and the module files of a dependency are counted nowhere; errors and warnings count its own diagnostics, among them the one of each dependency that failed.

    4.16 Bindings #

    A binding of a curated module records what a person read when they wrote it: the provision it binds, the release of the dependency they read it in, and two hashes of what they read. Of a curated workspace that depends on the demo workspace, conformance/fixtures/workspace/demo of the release 42-7:

    • What binds names is an address of a dependency, written out or reached through a citation, as Curated modules describes; sizes_binding binds /zz/demo/t1/s2. An alias of a unit stands for the unit, as it does for a reference, and an address wins over an alias.
    • release is the release of the dependency the binding was written against.
    • provision_hash is the tree hash of the provision: of its number, heading, status and text and of the tree hash of each child, so that a change to any word of it or below it changes it.
    • notes_hash is the hash of the enacted layer of the unit the provision lies in, which holds its enacted notes.

    Both hashes are 64 lower-case hexadecimal digits, which the check of one module requires (E710). The check of a workspace compares them, in phase two and from the interfaces alone, with what the dependency holds now. A binding is stale, for the first of these reasons that holds:

    ReasonWhen

    A binding whose provision changed in a word is stale, and so is a binding of the section that holds it; a binding of a sibling is not. A new enacted note of a unit makes every binding of a provision of that unit stale. Nothing else makes a binding stale:

    • Editorial matter, the source credit, the editorial notes and the footnotes and their markers, is in neither hash, so a change to it makes nothing stale.
    • A note set out under a container enters the enacted layer of no unit.
    • The release a binding records is compared with nothing. It is shown in the warning beside the release of the dependency, so that a reader sees against which release the binding was written; against a dependency of another release in which neither hash changed, the binding is not stale.
    • A dependency that fails a check makes no binding stale: the bindings of what lies below its prefix are not judged, and its one diagnostic is the report.

It never changes the exit status and is counted in warnings of the summary line and of the check report. Its message names the binding, the address, the reason, the release the binding records and the release of the dependency, and says what to do.     4.17 Change sets #

    A change set says what changed between two releases of one corpus: which provisions, notes and containers were added, removed, moved or amended between two generated workspaces of one prefix, each the import of one release, by layer, and which bindings of given curated workspaces are stale against the newer one. fidryn changes OLD_DIR NEW_DIR prints it as JSON, fidryn.change-set/v0.1, whose JSON Schema is change-set-v0.1.json, or as the text of a commit message, under which a release enters a repository of the imported law.

    Each of the two workspaces is read as fidryn check reads it (How a workspace is checked), through phase one and the cache; a workspace that has an error ends the command with its diagnostics, and no change set is made. Then the two are compared from their interfaces. A unit whose three layer hashes and the addresses of whose provisions are equal on both sides is not read again, nor is a container whose hashes are equal. The notes, the containers, and the units on one side only are compared from the interfaces alone. Only a unit whose operative or editorial layer or whose provisions differ, a container whose editorial layer differs, and a unit on one side whose top provision has the kind and the status of a provision on the other side only, so that it could have moved, are opened, and their provisions, credits and footnotes compared. A module file that is opened is held to the BLAKE3 of the bytes its check accepted, which the lock records: a file that changed after the check read it ends the command with an E730 that names it, and enters no change set.

    4.17.1 The lists #

    Every list holds addresses, and every list is sorted by the bytes of its addresses; a moved entry is {"from": ..., "to": ...}, sorted by from and then by to.

    A provision is listed for what is its own, and at one place. Its own words are, in order, the text of each paragraph and subheading of its own text parts, those in the cells of its tables included, with its links, superscripts and subscripts, each quoted content whole, and the source of each image: a link added to words, or taken from them, amends the text. Its own structure is its kind, its number, its heading and its status; its text parts and children in their order, each text part by its role and by the kind of each of its blocks, a paragraph, a subheading, a table, quoted content or an image, and each child by its address; and the shape of its tables: the group of each row, and the header, the spans and the kinds of the blocks of each cell. A paragraph that becomes a subheading with the same words amends the structure, and not the text. A provision may be in both lists. A provision whose tree hash changed only because something below it changed is in neither: a word changed in a subsection lists the subsection, and not its section. A subsection added to a section is added, and the section is amended_structure, since the addresses of its children changed; the children of the subsection are not listed. A column added to a table changes its shape, and its words when its cells hold any.

    A footnote marker is no word of the text it stands in, so a marker that is added, removed or renumbered changes editorial.footnotes_changed of its unit or container and nothing in operative. Of the top provision of a unit, its aliases, the container it is within, its source and its positive-law flag are not compared: a unit that leaves one container for another lists the two containers, whose members changed, and not the unit. The credits and the footnotes of a module on one side only are not listed, since the module is.

    4.17.2 Moved provisions and notes #

    added and removed are first reduced to their highest provisions. Among the entries that remain, a removed and an added provision are one moved entry, and are taken out of the other two lists, when their tree hashes are equal once each one's own number is left out: the tree hash of Hashes computed with the frame of no number, F(0x04, empty), in place of the provision's number, and the tree hash of each child as it is (fidryn_provision::changes::unnumbered_hash). A section renumbered and otherwise unchanged has moved, and it carries its children with it: they are not listed. Each removed provision, in the order of the addresses, is paired with the first added one, in the order of the addresses, that has an equal hash and is not paired yet. So the provisions on the old side only, reduced to their highest, are exactly removed together with the from of moved, and those on the new side only added with the to.

    Notes are compared by their note hashes, which hold neither the address nor the layer of a note, in two steps. Like-named notes are paired first. Two notes of one unit or container are of one family when their addresses differ only in the ordinal that marks like-named notes: a last segment that is a whole number of 2 or more, written in ASCII digits with no leading zero, after an address that is itself the address of a note of the module on that side. Within one module, one layer and one family, an old and a new note of equal hashes are paired, each old note, in the order of the addresses, with the first new one, in the order of the addresses, that has an equal hash and is not paired yet. A pair at one address is unchanged and is listed nowhere; a pair at two addresses is one moved entry. So a note inserted before two like-named notes is added at the address of the first, and the two, whose text did not change, have moved, each to the ordinal after its own. The pairing stays within a family, since many notes are the same words in different units: a note amended to the words of a note of another unit is amended, and has not moved there.

    The notes that remain are then compared by address: one at an address that a remaining note on the other side has is amended, and one at an address that none has is removed or added. A removed and an added note are one moved entry when their note hashes are equal, paired in the same way as provisions across the workspace: a note whose address changed and whose text did not has moved, as the notes of a renumbered section do, and so does a note whose address names another law while its text is the same.

    A note whose text changed has no note of equal hash on the other side, so it is compared by address, with whatever unpaired note stands at its old address on the other side. When one does, the address is amended, and what the old note is compared with may be another note: of two like-named notes before which a note is inserted, an amended first is amended at the first address, where it is compared with the inserted note, and its new text is added at the second. When a paired note took its old address, the changed note is removed there, and its new text is added at its new address: an amended second, after an unchanged first that moved to its address, is removed at the second address and added at the third. In neither case can a change set tell that the note at the new address is the old one amended, since a note has no identity but its address and its text.

    4.17.3 Stale bindings #

    With --bindings DIR, each binding of the curated workspace in DIR is judged against the new side by the rule of Bindings, whatever release that workspace is pinned to and whether or not its pin is satisfied: the change set answers which bindings would be stale if the pin moved to the new release. The modules of DIR are read by phase one alone, and an error there ends the command; the names of its curated modules are resolved against its own modules and those of the new side, a binding whose name does not resolve is left out, and so is one whose address lies below another prefix than the new side's. A directory given twice, the same once its path is resolved, is read once. Each entry names the curated workspace by the name of its manifest, the module that declares the binding, the binding, the address it binds and the reason; the entries are sorted by workspace, module and binding, and an entry that two copies of one curated workspace both give is listed once.

    4.18 The ingester for the United States Code #

    fidryn-ingest-uscode imports the United States Code from the official XML release point published by the Office of the Law Revision Counsel. It reads the archives of one release, each verified against its retrieval record, into the units and containers of the model, with the definitions of each unit that Definitions describes, which fidryn ingest uscode writes as a generated workspace with the prefix /us/usc. It is the one crate that knows the Code's titles, the publisher's elements and their status values; the command line names the Code only to choose it, and the checker and the writer of a workspace know none of them. Its rules follow four principles: no operative word is dropped; nothing is invented; an element the rules do not name is refused, not skipped; and what is by rule not imported is counted.

    4.18.1 What it reads #

    A release is a directory that holds the publisher's zip archives and, beside them, nothing but their retrieval record, retrieval.json. Before it reads a document, the ingester:

    • reads the record, and refuses a directory that has none; the record is opened only when it is a regular file, so that a symbolic link, a directory, a pipe or a device in its place is refused before it is opened, and it is read through a bound of 1 MiB, past which it is refused;
    • recomputes the size, the SHA-256 and the BLAKE3 of every archive, and refuses one that differs from its record, the files the record does not list, named in the order of the bytes of their names, and an archive it lists that the directory does not hold;
    • refuses a member whose name is not usc, two digits, an optional a or A, and .xml, a member larger than 512 MiB, whatever its header declares, and a release in which two archives hold a member of the same name.

    Each member holds one title, or the appendix of one: usc05A.xml holds the title the publisher designates 5a. Nothing is written beside the archives.

    A document is refused when:

    • it has a document type declaration or an entity declaration;
    • its root is not uscDoc in the namespace http://xml.house.gov/schemas/uslm/1.0, or its schema location names a file other than USLM-1.0.15.xsd;
    • its docPublicationName is not Online@ followed by the release of the retrieval record, where each en dash (U+2013) of the name is read as a hyphen and no other character as another;
    • it has more than one property is-positive-law, or one that is neither yes nor no;
    • an element stands where its class does not allow it, or is in no class below; or text stands where only elements may;
    • a ref has neither an href nor the class footnoteRef, or has both, so that it would be at once a link and a footnote marker; a link, a superscript or a subscript stands inside another, or a footnote marker inside one; a footnote marker holds an element; a marker names no footnote of its module, or two footnotes of one module have one id; or a footnote holds a signature, a subheading, a heading or another footnote;
    • normalization composes one character out of characters on both sides of the boundary of a link, a superscript, a subscript or a marker;
    • an identifier holds ~, or gives no address, as none is given by an identifier of a unit or a container with an empty member, which two spaces in a row or a space at either end make, by an empty identifier, and by an identifier of a provision that begins with a space;
    • a level has a second num or a second heading;
    • a note stands in quoted content anywhere but directly in it or in one of its levels, such as in a paragraph, a text part, a table cell or another note of it;
    • a span of a table cell is not a whole number written in ASCII digits;
    • a br, an img or a column holds content, white space alone included, or an img has an attribute other than src;
    • a signature holds anything but name and role, a footnote that stands directly in it included;
    • a unit or a container has a second source credit, or a source credit stands anywhere but directly in one;
    • a cross heading has no topic, or one that is not one word of ASCII letters and digits beginning with a letter; or a topic of a note holds a white-space character other than U+0020, at which topics are split;
    • the law a note cites first is a reference of fewer than four segments, or one whose second, third or fourth segment holds a character that an address segment cannot hold;
    • an element stands more than 64 deep in its module, or a container more than 64 deep among the containers of its file: the element of a unit or a container stands at depth 1 of its module and each element inside it one deeper, except a unit or a container that is a member of a container, which begins a module of its own, and the top container stands at depth 1 among the containers. 64 is the deepest nesting of a module that the grammar of edition 2 reads, and a module holds no block deeper than the elements it is read from, so the check never refuses a module the ingester writes for its nesting; release 119-142 nests at most 17 deep in a module;
    • the document holds more than 8,388,608 nodes (2^23: elements, runs of text, comments and processing instructions, and not attributes), three times the 2,703,416 nodes of usc42.xml of release 119-142, its largest member;
    • a status is not one of the 19 values of the publisher's schema: proposed, withdrawn, cancelled, pending, operational, suspended, renumbered, repealed, expired, terminated, hadItsEffect, omitted, notAdopted, transferred, redesignated, reserved, vacant, crossReference, unknown.

    A refusal names the archive, the member, the element, the line it starts on, and the identifier of the element or of its nearest ancestor that has one.

    The flag of every module of a document, its positive_law, is the document's property is-positive-law: true for yes, false for no. A document may have no such property, and then its modules have no flag: they declare no positive_law, and the text record of each of its units has "positive_law":null.

    4.18.3 Notes and their layers #

    Each note in a notes element is a note, except a cross heading (role="crossHeading"), which opens a group named by its topic and is not itself a note. So is each note that stands directly in a level and is neither a footnote nor a release note. A note belongs to the unit or the container it is anchored in. Its topics are its topic attribute split at U+0020 and no other character, with the empty members dropped: an empty attribute, or one of spaces, gives no topic, and two spaces between two words give two topics. Its group is the topic of the nearest cross heading before it in its notes element, and ungrouped when there is none or the note stands directly in a level:

    GroupLayer
    editorialNoteseditorial
    ungrouped, with one of the topics removalDescription and historicalAndRevisioneditorial
    any other: statutoryNotes, execDoc, courtRules, any other ungrouped note, and any group word a release introducesenacted

    • <law> is the origin of the note's first quoted content when it begins /us/pl/, /us/act/ or /us/stat/; otherwise the href of the first link that begins /us/pl/ or /us/act/, taking the note's heading and then its blocks in order, where a link in a footnote and a link with no words do not count. Of that reference the first four segments are kept and the last three joined by full stops: pl.999.2, act.2099-07-30.ch9, stat.999.10. A note with neither has nolaw.
    • <heading> is the text of the note's heading with the letters A to Z put in lower case and every run of characters other than ASCII letters and digits written -, without - at either end, cut to 60 characters and again without - at its end.
    • Of a note with no heading, or whose heading leaves nothing by that rule, <heading> is noheading when it has a law, and, when it has neither, h. followed by the first 16 hexadecimal digits of its hash.
    • When several notes of one anchor agree in all three parts, the second in document order gets /2, the third /3.

    4.18.4 How it gives addresses #

    An address is the publisher's identifier except for the later holders of a repeated identifier, the elements without one, and what stands inside either:

    1. A unit or a container with an identifier. An identifier that holds a space is a list: its first member is the identifier used, and the other members are aliases. A list with an empty member, which two spaces in a row or a space at either end make, and an empty identifier give no address, and the document is refused. An identifier whose last segment holds three full stops in a row stands for a range, as s44...46 does: it is used as it is, and its aliases are its two ends, the identifier cut before the full stops and the identifier with its last segment replaced by that segment's leading lower-case letters followed by what stands after the full stops. When the two ends differ only in a whole number at their end, the second not smaller than the first and at most 999 above it, every number between them gives an alias as well; a member of a range whose number is followed by a letter gets no alias. The address is the identifier, unless a unit or a container before it in the release, taking the members in the order of their names and the elements in document order, already has it; then it is the identifier followed by ~2, by ~3 for the next, and so on.
    2. A unit or a container without an identifier. The address of the container it stands in, or the prefix for the top element of a file, followed by ~<tag>.<n>, where n counts from 1 the elements of that tag without an identifier in that place, in document order.
    3. A provision inside a unit. The address of its parent followed by the last segment of its identifier, of its first member if it lists several, and by ~2, ~3 when a sibling before it already has that address; without an identifier, followed by ~<tag>.<n> as in rule 2. An identifier that is empty or begins with a space has an empty first member and gives no address, and the document is refused; a space after the first member changes nothing.
    4. An alias that is the address of a unit, a container or a provision is dropped, and so is one the element already has.

    The count of rule 1, and that of rule 2 for the top element of a file, run over every member of the release that the archive directory holds, in the order of their names, whichever titles are written: an address depends neither on the titles chosen nor on the number of workers. The lock's addresses counts the elements whose address got ~2, ~3 by rule 1 or 3 (disambiguated), the elements whose own segment is ~<tag>.<n> (assigned), and the aliases kept (aliases). What stands inside such an element is not counted again.

    4.18.5 What it does not import #

    Some of what a document holds is by rule not imported, and the lock's not_imported counts it:

    Not importedCounted as

    a link that has no words, or white space alonelinks_without_words
    the label of a note group, the heading of a cross headingnote_group_headings

    What a cross heading holds after its heading is imported, as a note of the group it opens.

    4.18.6 What the command writes #

    fidryn ingest uscode ARCHIVE_DIR --out DIR writes the workspace with GeneratedWriter (Writing a generated workspace): the manifest, of the name uscode, the kind generated, the prefix /us/usc, the release of the record and the running toolchain's version; a module for each unit and container of the titles chosen, every title by default; the lock, whose generator is fidryn-ingest-uscode at the same version, whose artifacts are the archives and members whose modules the run wrote, as the record gives them, and whose counts are those above; and last the coverage ledger of the workspace. The numbering of addresses still runs over every member of the archive directory, as How it gives addresses says.

    The bytes it writes depend on the archives, on the titles chosen and on the toolchain's version, which the manifest and the lock record, and on nothing else. No time is written but the retrieval times the record gives, and no path but the paths of the files inside the workspace; neither the host, its user, its time zone, the working directory nor the number of workers changes a byte. Two documents that differ only in their element ids, their publication name, the creation time of their metadata and their release note give the same modules, and locks that differ only in release and artifacts.

    4.19 The coverage ledger #

    A generated workspace holds at its top its coverage ledger, coverage.json, fidryn.coverage/v0.1: what the workspace holds, in counts. The writer writes it last, after the lock, through a temporary file like every file of a run, and the lock does not list it. fidryn coverage DIR prints it, counted again from the files of the workspace as they stand; the two are the same, byte for byte, while no file is changed. No check reads it. Its JSON Schema is coverage-v0.1.json.

    fidryn_provision::records::coverage counts it from the interfaces of the modules, the index of their addresses below the prefix, which gives each reference its outcome as the check of the workspace does, the manifest and the lock, and from nothing else: it reads no module's source and nothing outside the workspace. A unit and a container are counted, with their notes, footnotes, references and definitions; a curated module is counted nowhere. The keys, in their order:

    4.20 The sample #

    The repository holds a sample of the Code under samples/uscode/ (its README): the publisher's archives of three whole titles of the release 119-142 of the official XML release point published by the Office of the Law Revision Counsel, Title 1, Title 11 Appendix and Title 45, and what is imported from them.

    • archives/ holds the archives, exactly as served, and their retrieval record, retrieval.json.
    • profile.json holds the counts of the archives that conformance/usc_profile.py prints, by the counting rules of usc-counting-rules.md.
    • workspace/ holds the generated workspace that fidryn ingest uscode samples/uscode/archives --out DIR writes: its manifest, its lock, its coverage ledger, and a module for each of the 563 units and 72 containers of the three titles, 638 files in all. It is written by cargo xtask uscode-sample --update and never by hand. The page Coverage shows the figures of its ledger.
    • curated/ holds a curated workspace written by hand that depends on workspace/, at ../workspace, pinned to its release and to the BLAKE3 of its lock. Its one module gives names to provisions of the sample, a whole section, a subsection and deeper provisions, a rule of the appendix title and a note, and binds one section, with the release of the sample and the two hashes that fidryn text --hashes prints for it; it holds no text of the Code. fidryn check samples/uscode/curated --no-cache checks it with its dependency.

    cargo xtask uscode-sample, which cargo xtask ci runs, holds the sample to nine things, in this order, and fails with a message that names the first difference when one of them does not hold:

    1. every archive has the size, the SHA-256 and the BLAKE3 that its record gives, and the record names every archive and no other;
    2. an ingest of the archives into a temporary directory writes, byte for byte, every directory and file of the committed workspace, its ledger among them, and nothing else;
    3. an ingest on one worker writes the same bytes as an ingest on eight;
    4. fidryn check samples/uscode/workspace --no-cache finds no error, and fidryn coverage samples/uscode/workspace prints the committed coverage.json, byte for byte;
    5. profile.json is, byte for byte, what the script prints for the archives; its counts of references by layer and outcome, which the script works out by the rules of References on its own, are those of the check report; and every count that the profile's import and the ledger's totals both hold is the same in both, from the units and the provisions to the notes, the images and what was not imported. Only the ledger counts definitions, definitions and definitions_by_kind, since that script extracts none, and the profile's prefix and release stand at the top of the ledger, where they are compared;
    6. the text of every provision, container, note, source credit and footnote that fidryn text samples/uscode/workspace --json reads back from the modules equals, line for line, what conformance/uslm_text.py reads from the publisher's XML by the rules of the reading, which it implements on its own, sharing no code with the ingester;
    7. the definitions that conformance/usc_definitions.py finds in the archives, by its own implementation of the rules, are those that the modules of the committed workspace hold, as the check reads them, field for field (A second implementation of the rules); the step names the module of the first definition that differs;
    8. the check of curated/ with its dependency finds no error and no warning, a pin that is no longer the lock's (E740) among the errors and a stale binding (W750) among the warnings, counts at least one citation, and gives every citation of it the outcome exact; the step names the file and the first thing that is wrong, and the curated sample when it counts no citation;
    9. the table of Coverage, between the markers <!-- coverage-table:begin --> and <!-- coverage-table:end -->, is the one the committed ledger gives.

    The fidryn commands run in the process of the step, as the binary runs them. The step makes its temporary directories under the system's directory for temporary files and removes them whether it passes or fails, and its checks keep no cache, so it leaves the repository as it found it: only --update writes, the workspace, then, in the curated manifest, the release and the lock digest of its dependency and its toolchain, and then the table of docs/coverage.md between its markers, and nothing else; it never touches the curated module. The ledger is not listed in the lock, so writing it moves no pin. When --update changes the table of docs/coverage.md, cargo xtask site is run after it to render the page again, since cargo xtask ci fails while the site is not what the documents give.

    4.21 Limits #

    Each of these is true of the code at this version. They say what the code does and does not do where a reader of the sections above could expect more.

    4.21.1 Workspaces and the cache #

    • A dependency of a curated workspace is a generated workspace, named by a path relative to the directory of the manifest. A curated workspace cannot depend on another curated workspace (E740), and a dependency named by an absolute path is refused (E730).
    • A command reads a manifest, a lock and an entry of the cache only from a regular file of at most 64 MiB (67,108,864 bytes), more than nine times the lock of the import of the whole Code. A symbolic link, a named pipe, a device or a directory in the place of a manifest or a lock is refused before anything is opened, as the check refuses a symbolic link, and a larger file is refused, with a sentence that gives the bound, without being read; such an entry of the cache is a miss, and an entry that would be larger is not written.
    • A check trusts its cache: an entry written by hand under the key of a module's bytes is taken as that module's result. A cache belongs where only people one trusts can write, and the default is a directory of the user, outside every workspace (The cache).
    • The check compares the cache's directory with the directory of each dependency, and not what lies below the cache's directory. When a symbolic link there, such as a v1 that leads into a dependency, is followed, the check writes its entries inside the dependency.
    • The writer of a generated workspace tells an earlier output from another .fr file by its head alone. A module of the prefix at its own path whose head lies past its first 64 KiB, after comments, is refused, though the check would read it; and a module that a person changed below its head is an earlier output, which a run writes again or removes.
    • A check that is killed while it writes an entry of the cache leaves the temporary file of the entry, whose name begins with a dot and ends in .tmp, in the cache. Nothing reads it, and nothing removes it.
    • A module file name such as s1932~2.fr has the shape of a Windows 8.3 short name. On a volume that gives files such short names, it could be the short name of another file of the same directory.

    4.21.2 Diagnostics #

    • fidryn check prints a diagnostic of a module of edition 2 as FILE: CODE Title: message, with no line and no column: the span the diagnostic is about is recorded and not printed. A message that names what it is about, such as the provision whose hash does not match, says where it is; "text is not normalized" does not.
    • E740 has the title PinMismatch also when a dependency fails for another reason than its pin: no directory, no manifest, a curated workspace, no lock, or errors of its own.

    4.21.3 Modules written by hand #

    • A module's definitions, its aliases, within, source and positive_law are in no hash of the module (Hashes), and the check of a definition holds its form and not its region, its basis or its note (What the checker verifies in one module). In a generated workspace the lock holds the BLAKE3 of the bytes of every module file, so a module edited by hand there fails the check (E730) unless the lock is written again with it, and then the digest of the lock changes, which a curated workspace that depends on it reports (E740). A module checked by itself, and a module of a curated workspace, which has no lock, pass the check with a definition whose region, basis or note was edited by hand.
    • fidryn text prints the strings of a module as they are. Every control character that is no white space passes normalization and the check: U+0000 to U+0008, U+000E to U+001F, U+007F, and U+0080 to U+009F but U+0085. Among them is the escape, U+001B, that begins the sequences a terminal acts on, and fidryn text writes such a character to the terminal as it is. A module written by hand can hold any of them. The importer writes none below U+0020, since XML cannot hold one, and keeps U+007F and the C1 controls but U+0085 where the publisher's XML holds them.

    4.21.4 Definitions #

    • The rules read definitions in a closed list of forms and in no other (Definitions), and they do not find every definition. D16 lists the forms they leave out, with their counts measured on release point 119-142, the whole Code, and the records that keep a form of the source as it is.
    • Whether a text holds an end of a sentence is judged on its own characters (D4.2), so reach words may end with a full stop. Release point 119-142 has one such record, at /us/usc/t42/s1396b–1/b: its words are In this section., with no region and the basis unresolved.
    • unstated is given when neither the paragraph nor a chapeau above it states a reach. A reach stated in a sibling provision, such as "In this section" as subsection (a) with the definitions in subsection (b), is not seen.
    • An exception written inside the text of a definition, such as "means a widget, except in section 5", does not narrow its region: the region is that of the reach alone.

    4.21.5 Change sets #

    • The credit and the footnotes of a unit or a container that is on one side only, and of a unit that moved, are in no list.
    • Where a footnote marker stands inside its provision is in no hash, and so in no list: a marker that moves within one provision changes nothing that a change set lists.
    • A superscript that the source does not mark as a footnote marker is text, even when it shows the number of a footnote. A provision that gained only such a superscript is in operative.amended_text, and a binding of it, or of a provision above it, goes stale. The cost is a false alarm, never a missed change.
    • A change of the aliases of a unit, of the container a unit or a container stands in, or of the positive-law flag of a file, is in no list; a unit that moves to another container lists the two containers, whose members changed. A title enacted as positive law between two releases, with no other change, gives a change set in which every list is empty, and the bases of its definitions, which follow the flag, are in no list either: definitions are in no hash.
    • Like-named notes are paired by equal note hashes alone, and a note has no identity but its address and its text. A note of a family whose text changed while another was inserted before it is compared with whatever unpaired note stands at its old address on the other side: that address is amended when one does, though what it compares may be the old note and the inserted one, and the note is removed there when a paired note took the address; its new text is added at its new address. No change set says that the note at the new address is the old one amended. Units and containers whose addresses ~2, ~3 mark as later holders of one identifier are not paired this way: they are compared by address.
    • The addresses of a family are taken in the order of their bytes on both sides, so …/10 comes before …/2: in a family of ten or more like-named notes, notes of equal text pair in that order, and one may be listed as moved from /2 to /11 where pairing by the order of the ordinals would leave it in place.
    • conformance/usc_compare.py --against checks the unions of the lists, as Change sets says. It cannot see a provision in the wrong one of two lists whose union it checks, or a wrong pairing of a move, and it compares neither the prefix, the two releases nor stale_bindings. The tests of fidryn-driver hold each list on its own.

    4.21.6 The ingester and the independent reading #

    • The ingester and conformance/uslm_text.py read these rare forms of the publisher's XML by one rule: a continuation or a proviso inside a content directly in a note; a note in quoted content anywhere but directly in it or in one of its levels; white space inside a br, an img or a column; an identifier with an empty member; the words of the class of a ref; a num or a heading among the words of a level of quoted content; a footnote inside a footnote; a table of contents inside another; and a footnote inside a release note. The rules are those of What it reads, The classes of elements, How it gives addresses and What it does not import.

    • They read three other forms differently. No release of 2026 holds any of them.

      • A comment or a processing instruction inside a br or a column: the ingester refuses it as content, and the independent reading, whose parser drops both, does not see it.
      • A schema location that the two take apart differently, so that one of them refuses the document and the other reads it: the ingester splits it into words at ASCII white space and the independent reading at any white space; the ingester takes the first file named for the publisher's namespace and the independent reading the last; and the independent reading refuses an odd number of words, where the ingester reads the pair it needs.
      • A note with the role crossHeading that stands directly in a title or an appendix and whose text begins Current through : the ingester takes it for the release note, which it does not import, and the independent reading reads it as a note of its own, ungrouped.

      On the first two, one of the readings refuses the document. The third is read by both and read differently, and shows only when the two readings are compared on that release: what conformance/uslm_text.py prints for its archives against what fidryn text DIR --json prints for its workspace. tools/replay_uscode.py makes that comparison for each release it replays, before it commits the release, unless it is given --no-readings, and compares the count of tables of contents of conformance/usc_profile.py with the ledger's; an import makes neither. Another form that the two read differently shows there when it changes a text record or that count. One that changes only another count of what is not imported, the footnotes or the links in tables of contents, the release notes, the links without words or the labels of note groups, shows in neither: the check of the sample compares every count that the profile and the ledger both hold, and does so for the sample alone.

    • The independent reading refuses the nesting the ingester refuses, by the same rule, but has no bound on the number of nodes of a document: it reads a document the ingester refuses for its size, given the memory, about 3 GB for a member of 64 MiB of empty elements.

    • A table of contents is not imported. The lock counts it (What it does not import).

    • No display citation is derived. The address is the one citation a module records, and no form such as "1 U.S.C. § 8(b)" is made from it.

    4.21.7 Fetching #

    • tools/fetch_uscode.py follows a redirect only to the host it asked, over https, and refuses any other, naming where it pointed. The retrieval record names the address the tool asked for, not the one a redirect led to.
    • It takes at most --max-bytes bytes in one response, 536,870,912 (512 MiB) unless that says otherwise, a bound with room above the largest archive the publisher offers, the archive of every title, and it refuses a larger response as soon as it has read one byte more.
